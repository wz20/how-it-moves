# Targeted repairs and honest evaluation

## 不再只说“阻塞”

`create.py diagnose PROJECT --out PROJECT/repair-v1.json` 会调用现有检查，输出阶段、精确错误、修复建议和审片失效信息。可加 `--review PROJECT/review-v1/review.json` 读取明确 rejected 的镜头意见。不会改源文件、降低阈值、自动审批或触发生图费用。

典型修复：
- 缺入口/遮挡：只给相应主体补图层或定位，不把整套主题重画。
- 门盖超出画幅：根据报错帧修改物件位置/真实支点/角度，检查全部开合路径。
- 取回的 ID 不存在：修正语义和依赖，不补一个“成功”标签。
- cue 太短/重叠：调整该句时间点或重新录制，不给整条视频倍速。
- 画面仍像 PPT：由视觉审阅指出占主导的文本和缺失操作，重设计该镜头；换颜色不是修复。

“局部修复”指作者/生图的修改范围。当前 final review 仍要求完整证据，视频仍完整渲染；没有实现智能补间、自动剪接或只重渲一小段。

最多两轮不能解决时交给有视觉能力的审阅者/用户诊断；不能让文字模型自称看过或听过。审阅者可以使用其他工具，但必须保留同一素材、因果和证据约束。

## 对比测量应怎样做

评测对象：How It Moves、Remotion+其Skills、HyperFrames+其Skills。测试前锁定实际版本，不把“工具已安装”当成效果证明。评测协议不替用户运行额外付费模型或上传文件。

1. 使用同一宿主模型、同一题目、同一输入资料和长度、同等生图/推理预算；保存版本、次数、时间、失败和人工修订。
2. 使用至少三类机制：反馈改变下一步、保留原件的检索、副本失效/资源回收。不能只考某个库已有的专属样例。
3. 每题要求新的视觉世界和主体。在同一系统内部再换三套不同形状/端口的素材，检查同一动作能否适配。
4. 先做技术事实核验，再让不知道工具名称的至少两位审阅者评价素材吸引力、操作可辨认、对象连续、阅读/听音节奏。发生分歧保留各自评分。
5. 给观众提与机制有关的理解问题，例如“原资料被删除了吗？为什么此时才重试？”记录答案，不把点赞当成理解率。
6. 报告成功率、耗时、真实调用成本、返工轮数、内容错误、评分分歧；自动回归测试不代替上述指标。

结果登记中的未测项目用 null/not_run，而不是0分、100%或空泛“通过”。当前版本随附的是工程测试与合成素材验证，没有完成弱模型评测或跨引擎盲测。

## 制作质量标准保持不变

真实新生图、同项目身份保持、无框+段落替代品、可读文字、不冒用生成记录、未审不交付。程序无法认证生成票据，无法理解所有隐喻，也不能证明任何新图片都好看。语义动作库降低已支持操作的工程负担，但没有消除主题理解与美术设计工作的难度。

## v0.8：区分缺机制和看不见机制

- E_MECHANISM_REQUIRED：先补事件计划，不加大图片缩放。
- E_MECHANISM_DIVERGENCE：声明的变量效果与操作编译器不符；改合同或已验证操作，不能只改字幕。
- E_VISUAL_OCCLUDED：事件状态正确，但隐藏该结果图层后像素没有变化；修可见性/遮挡/层序，仍需视觉判断。
- E_EVENT_REVIEW：查看每事件前态、接触、提交、后态和连续播放；补真实审片证据，不复制长段空话。

未知题材冷启动要冻结引擎版本，记录真实生图、额外专用代码、人工修复、失败和完成率。门禁把全部作品拦下不是高质量成功率。当前新增浏览器测试仍是合成工程测试。真实生图冷启动、弱模型成功率、盲评与受众理解保持 not_run / not_tested。
